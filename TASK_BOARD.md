## Integration contracts (both agents)

- `POST /api/visualizations`: `{ image: base64Jpeg, spaceType, productId, style, placement, dims? }` → `201 { id }`; errors use `{ error }` with the source plan's status codes.
- `GET /api/visualizations/:id`: `{ status, items: [{ productId, quantity }], choices: { spaceType, style, placement }, before, after }`; status is `processing | succeeded | failed`.
- Same-form result link: `/?visualization=<id>#enquiry`. The homepage restores it with `GET /api/visualizations/:id`; there is no result-to-enquiry page handoff.
- `POST /api/enquiries`: `{ space, light, size, notes, name, contactMethod, contact, productId?, visualizationId?, photo? }` → `201 { id }`.
- `toJpegBase64(file, maxEdge?)` returns raw base64 without a data-URL prefix; server accepts JPEG only, max 8 MB decoded.
- Total plant makeover (spec `docs/superpowers/specs/2026-10-04-total-plant-makeover-design.md`): `POST /api/visualizations` with `{ mode: "makeover", image: base64Jpeg, spaceType, style, items: [{ productId, quantity }], dims? }` (1 to 8 plants in total, no `productId`/`placement`) → `201 { id }`; `400 { error }`; `404` while the server flag `MAKEOVER_ENABLED` is not `1`; `429` at the cap; `502` when the designer or Kie cannot start (slot refunded).
- `GET /api/visualizations/:id` also returns `mode: "single" | "makeover"`, `rationale: string | null` and `layout: { furniture: string[], plants: [{ productId, count, placement, why }] } | null`. Insert this model-written text with `textContent`, never `innerHTML`. Show the approximate-AI label and "Try another layout" (a new request; it uses one more daily slot).
- Static Astro; no new frontend dependencies, cart, webhook, email notifications, or multi-plant designer in this scope, except the total plant makeover above.
- Agree and record any contract change here before the other agent integrates it.
